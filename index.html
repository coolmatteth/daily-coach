01The system

Not a chatbot — a schedule of narrow agents, each owning one job, coordinating through Notion as the shared data layer.

Daily training planner4:31 PM · daily
Reads the Athlete File and 14 days of logs, programs tomorrow's session, delivers it to Telegram with its reasoning.
Daily calendar sync10:13 PM · daily
Reconciles logged sessions onto a calendar — grounding the planner in what day it is and what I actually trained. Killed a whole class of hallucinations.
Briefing retry9:31 PM · daily
If the primary run failed, re-runs the full flow five hours later. Idempotent — the delivery record makes a duplicate send impossible.
Weekly athlete file updateSunday evening
A second agent maintains the first agent's ground truth: rescans the week's logs, updates PRs, current build, and the training-block clock.
Block debriefevery 5 weeks
Closes out each training block: what moved, what's earned next. Banned from reciting stats without a consequence attached.
Edge workeralways on
The only component allowed to send. Enforces deterministic guards in code: a dated PR-window gate, duplicate and out-of-window delivery rejection, spend limits.

The guardrails are scar tissue. Early on, a failed API call got retried in an endless loop — $3.64 and 820K tokens burned on the same errored request — so now agents fail cheap and loud: spend limits, retry caps, errors surfaced where I'll see them. A 2 AM platform re-run once sent a duplicate briefing and archived a live workout sheet — so delivery windows are enforced in worker code, not in prompts.

From the agent's run log — why this plan
  1. Computed the block clock first — day 4 of 35, inside the open PR window. Every downstream decision keys off this.
  2. Caught a plan override — I trained push instead of the workout it had prepared, logging it in chat. It counted the real session as the record instead of marking the day "skipped."
  3. Found a travel note — away gym for three days, so it built the plan around cables and dumbbells it could count on.
  4. Picked pull — longest gap (15 days), and it doesn't load the flagged knee. Dropped rear-delt work because yesterday's session already hit it.
  5. Held the PR — window open, but yesterday's pressing was below proven weight and a shoulder flag was inside its cooldown. Two vetoes — and it says so in the briefing instead of silently deciding.

03How I know it's good

GroundingThe agent works from an Athlete File — who I am, current build, PRs, injury state — updated weekly by a separate agent that rescans the logs. Before that file existed, it hallucinated PR weights and workouts I'd never done. [MATT — approve/edit]

Hard constraintsDomain rules are encoded as checks the output must pass, not suggestions: heaviest compound first while fresh, a block ceiling so it can't overprogram, PR attempts only in the first half of a fresh block — and that last rule is re-verified by deterministic code, not the model. [MATT — approve/edit]

Judgment as the evalBad outputs are obvious to someone who's trained for years: weights that contradict history, machines that don't exist, exercises in an order no lifter would run. I've been the eval harness every day since May. [MATT — approve/edit]

Scaling it honestlyMy checks live in my judgment, and that doesn't scale. To productize this I'd formalize them into an automated eval — a golden set of user profiles with known-good programming, every model or prompt change scored against it, failures tracked by type: grounding errors, constraint violations, hallucinated equipment. New personas (yoga, barre, no history) would need new guardrails before I'd trust it with them. [MATT — approve/edit]
