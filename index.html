Constraints the agent has to respect

I train around a knee limitation (patellar tendinopathy). The rules live in the Notion Athlete File as data, not in the prompt — and the ones that matter most aren't trusted to the model at all.

  • Knee-loading lifts cap at ~10% weekly jumps — the agent proposes loads inside the ramp, whatever I ask for.
  • 48-hour rule — after any knee-loading session, the next one is gated on how the knee reads two days later, so the agent spaces leg days and rides apart.
  • One PR attempt max per session, zero while a joint is flagged — and PR attempts are only legal in a dated 14-day window each training block.
That last rule is enforced twice. The model is instructed to respect the window — and then a Cloudflare Worker re-checks the dates in plain TypeScript and strips any PR flag the model shouldn't have set, failing closed:

How it works

Notion is the data layer — an "Athlete File" page holds the rules, injury protocol, and working weights; a database holds every logged session.
Scheduled Claude agents (cloud cron, no server of mine) read it each evening, draft the plan, and hand it off — they can't message me directly.
A Cloudflare Worker is the only thing that can send: it enforces the PR-date gate, rejects duplicate or out-of-window deliveries, then pushes to Telegram and creates the day's editable worksheet in Notion.
A retry agent re-runs 5 hours later if the primary failed — the worker's delivery record makes the retry idempotent.
  • Every guard exists because of a real failure: a Telegram retry storm → idempotent webhook; a 2 AM platform re-run that sent a duplicate and archived a live workout → the delivery-window rejection; the model getting PR-happy → the date gate in worker code.
